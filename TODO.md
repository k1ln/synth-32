# synth-32 Workstation — Implementation Plan

## Hardware Context

- **Board**: Waveshare ESP32-P4 (dual-core 400 MHz RISC-V, ~768 KB SRAM, 32 MB PSRAM via Hex-SPIRAM 200 MHz)
- **WiFi**: ESP32-C6 companion chip — handles all 802.11 WiFi; P4 has no native WiFi radio. Connected via SPI using Espressif's `esp_hosted` framework: C6 runs `esp_hosted` slave firmware, P4 runs standard IDF WiFi/socket/HTTP APIs as if WiFi were on-chip. All AP setup, HTTP server, WebSocket server, audio streaming, and SD card file uploads run on the P4 side transparently.
- **Display**: MIPI-DSI HX8394 1280×720, RGB565, 3× framebuffers live in PSRAM (~5.25 MB)
- **Audio**: ES8311 DAC/ADC via I2S, 48 kHz / 16-bit stereo
- **Flash**: 8 MB (partitions.csv must account for SD as primary storage)
- **Touch**: GT911 capacitive
- **Sounds**: 35 drum/sample kits, 1859 audio files in mixed formats (~437 MB total) — must live on SD card as WAV

## Phase 0 — SD Card Infra & Delta Upload

### 0.0 ESP32-C6 WiFi bring-up (esp_hosted)

The P4 has no WiFi radio. The C6 companion chip provides it via SPI using Espressif's
`esp_hosted` framework. This must work before any network feature can be tested.

**C6 side (flash once):**
- Flash the pre-built `esp_hosted` slave firmware onto the C6 (`idf.py -p <port> flash` from `esp-idf/examples/esp_hosted/slave`)
- No custom C6 code needed — it runs as a transparent WiFi coprocessor

**P4 side:**
- Add `espressif/esp_hosted` to `idf_component.yml`
- Configure SPI host, MOSI/MISO/CLK/CS pins, and handshake GPIO in `sdkconfig` / `Kconfig`
- Confirm pin assignments don't conflict with MIPI-DSI, GT911 I2C (SDA/SCL), I2S, or SDMMC
- After `esp_hosted` init, standard `esp_wifi_*` / `esp_netif_*` / `esp_http_server` APIs work identically to a WiFi-native chip — no code changes needed elsewhere

**Verification steps:**
1. P4 boots, `esp_hosted` initialises over SPI
2. `esp_wifi_set_mode(WIFI_MODE_AP)` + `esp_wifi_start()` — AP `synth-32` appears on host
3. Host connects, `http://192.168.4.1/` returns a test response
4. WebSocket upgrade at `ws://192.168.4.1/ws` connects successfully

### 0.1 SD card driver
- Add `esp_driver_sdmmc` or `esp_driver_sdspi` to `CMakeLists.txt` and `idf_component.yml`
- Mount FAT filesystem at `/sdcard` using `esp_vfs_fat_sdmmc_mount`
- Store mount point root in a `#define SDCARD_ROOT "/sdcard"`
- SD SDMMC 4-bit on P4 (check BSP pin map) or fall back to SPI if pin conflicts with display

### 0.2 Audio format strategy

Source kits contain 4 formats — all 16-bit / 44.1 kHz:

| Format | Source files | Source size | On-SD format |
|--------|-------------|-------------|--------------|
| WAV (16-bit LE PCM) | 1347 | 374 MB | keep as-is |
| FLAC (lossless) | 384 | 23 MB (~60 MB decoded) | **convert → WAV** |
| AIFF (16-bit BE PCM) | 86 | 30 MB | **convert → WAV** |
| OGG Vorbis (lossy) | 37 | 944 KB (~3 MB decoded) | **convert → WAV** |

**All files are stored on SD as 16-bit little-endian PCM WAV.**

Rationale: FLAC/OGG decoding requires 40–80 KB working RAM and significant CPU per
active lane. 16 concurrent decoders would saturate the CPU before effects or synths
run at all. SD bandwidth (10–25 MB/s) far exceeds the 16-lane PCM stream (~6 MB/s at
44.1 kHz stereo 16-bit), so streaming raw PCM is the right tradeoff. AIFF is identical
to WAV but big-endian — byte-swapping per sample is wasted work.

The upload tool handles conversion on the host before transfer.

### 0.3 Sound directory layout on SD
```
/sdcard/sounds/<kit-name>/<file>.wav      ← always 16-bit LE PCM WAV after conversion
/sdcard/sounds/.manifest.json             ← generated by upload tool, lists sha256 per file
```

### 0.4 Delta upload over WiFi (AP mode, existing WebServer)
- **Upload tool (host side)**: Python script `tools/upload_sounds.py`
  - Requires: `ffmpeg` (for FLAC/AIFF/OGG → WAV conversion) and `requests`
  - Scans source `sounds/` dir; for each audio file:
    - If not already WAV: convert to 16-bit 44.1 kHz mono/stereo WAV via `ffmpeg -y -i <src> -ar 44100 -sample_fmt s16 <dst.wav>` in a temp dir
    - Compute sha256 of the (possibly converted) WAV
  - Connects to `synth-32` AP
  - `GET /sounds/manifest` → device returns current manifest JSON (filename → sha256)
  - For each local WAV: skip if sha256 matches manifest, else `PUT /sounds/upload?path=<relative>`
  - After all uploads: `POST /sounds/commit` → device rewrites `.manifest.json`
- **Device side HTTP handlers**:
  - `GET /sounds/manifest` — reads `/sdcard/sounds/.manifest.json`, streams JSON
  - `PUT /sounds/upload` — streams body directly to SD card file (never buffers whole file in RAM; use `esp_http_server` chunked receive with 4 KB stack buffer)
  - `POST /sounds/commit` — atomically swaps new manifest
- SHA256: use `mbedtls_md5` or `esp_sha` (hardware SHA on P4) — do it in streaming 4 KB chunks, zero heap overhead

### 0.4a Mobile file upload to SD card

### 0.5 Friendly domain names & mDNS

The device is reachable via three methods simultaneously, all resolving to the same HTTP
server and WebSocket endpoint. Users never need to type a raw IP.

**Method 1 -- mDNS / Bonjour (recommended, works on macOS/iOS/Android Chrome)**

```c
#include "mdns.h"

void mdns_init_synth(void) {
    ESP_ERROR_CHECK(mdns_init());
    mdns_hostname_set("synth-32");        // -> http://synth-32.local
    mdns_instance_name_set("synth-32 Workstation");
    // advertise HTTP service so browsers find it via service discovery
    mdns_service_add(NULL, "_http", "_tcp", 80, NULL, 0);
    mdns_service_add(NULL, "_ws",   "_tcp", 80, NULL, 0);
}
```

After connecting to the `synth-32` WiFi AP, any device resolves:
- `http://synth-32.local` -> web UI
- `ws://synth-32.local/ws` -> WebSocket control + audio stream

**Method 2 -- captive portal redirect (works on all phones on AP join)**

When a phone joins the AP, the OS probes a known connectivity-check URL
(iOS: `captive.apple.com`, Android: `connectivitycheck.gstatic.com`).
The device intercepts these with a DNS server that returns its own IP for all queries,
then the HTTP server redirects to the web UI:

```c
// Catch-all DNS: resolve every hostname to 192.168.4.1
// Use lwIP's DNS server or a minimal UDP DNS responder on port 53
// Any HTTP request to an unrecognised Host header -> 302 to http://synth-32.local/

esp_err_t catchall_handler(httpd_req_t *req) {
    httpd_resp_set_status(req, "302 Found");
    httpd_resp_set_hdr(req, "Location", "http://synth-32.local/");
    httpd_resp_send(req, NULL, 0);
    return ESP_OK;
}
```

Result: phone joins AP -> captive portal popup appears -> taps it -> opens synth UI.
No URL typing required.

**Method 3 -- raw IP fallback**

`http://192.168.4.1` always works as a fallback for devices without mDNS.
The upload tool (`upload_sounds.py`) uses this IP directly to avoid mDNS dependency.

**URL path summary:**

| URL | What it does |
|-----|-------------|
| `http://synth-32.local/` | Web UI (main entry point) |
| `http://synth-32.local/ws` | WebSocket endpoint (upgrade) |
| `http://synth-32.local/sounds/manifest` | GET sound manifest JSON |
| `http://synth-32.local/sounds/upload` | PUT sound file (upload tool) |
| `http://synth-32.local/sounds/commit` | POST commit manifest |
| `http://192.168.4.1/` | Same as above, IP fallback |
| `http://synth/` | Alias -- mDNS also registers short hostname `synth` |
| `http://synth32/` | Alias -- mDNS also registers hostname `synth32` |

The device registers three mDNS hostnames:
```c

// additional aliases via extra A-record trick or second mdns instance:

```
> Note: true multi-hostname mDNS on ESP-IDF requires registering separate service

**Dependencies to add to `idf_component.yml`:**

## Phase 1 — WAV Playback Engine (Low RAM, SD-Streaming)

### Design principle: stream from SD, never buffer whole files
- Each active WAV lane gets a **512-byte read ring** in PSRAM (not SRAM)
- A dedicated `sd_stream_task` (core 0, priority 10) refills rings from SD via `fread`
- Audio mixing task (core 1, priority 22) reads from rings — if starved, inserts silence

### 1.1 WAV file reader
```c
typedef struct {
    FILE       *fp;           // open SD file handle
    uint32_t    data_offset;  // byte offset of PCM data in file
    uint32_t    data_bytes;   // total PCM bytes
    uint32_t    pos;          // current read position in PCM data
    uint8_t     channels;     // 1 or 2
    uint32_t    sample_rate;  // native SR (may differ from 48k)
    uint8_t     bits;         // 16 or 24
} wav_file_t;
```
- `wav_open(path)` — reads 44-byte RIFF header only, seeks to `data` chunk
- `wav_read_frames(wav, buf, n_frames)` — reads n_frames × channels × (bits/8) bytes
- If native SR ≠ 48000: linear interpolation resampler (integer-math only, no floats in audio hot path)
  - Ratio stored as fixed-point 16.16

### 1.2 Stream ring buffer (per lane)
```c
#define STREAM_BUF_FRAMES 256   // 256 stereo frames = 1 KB in PSRAM
typedef struct {
    int16_t  buf[STREAM_BUF_FRAMES * 2];  // stereo, interleaved
    uint16_t write_idx;
    uint16_t read_idx;
    uint16_t fill;              // frames available
    bool     active;

    // Playback mode (mirrors sample_play_mode_t used in drum rows)
    sample_play_mode_t play_mode;  // ONE_SHOT / LOOP / LOOP_PING / GATE / SLICE
    uint32_t loop_start;   // byte offset of loop start in PCM data (0 = file start)
    uint32_t loop_end;     // byte offset of loop end (0 = EOF)
    uint32_t slice_start;  // SLICE mode: start byte
    uint32_t slice_end;    // SLICE mode: end byte
    bool     reverse;      // fill ring in reverse (read SD backwards)
    float    pitch;        // semitone shift ±24, applied via resampler ratio
    float    start_offset; // 0.0–1.0: initial playback position
} stream_ring_t;
```
- All `stream_ring_t` instances allocated in PSRAM via `heap_caps_malloc(…, MALLOC_CAP_SPIRAM)`

### 1.3 SD streaming task
- Runs on core 0; wakes every 2 ms via `vTaskDelay`
- Iterates all 16 lanes; for any active WAV lane with `fill < STREAM_BUF_FRAMES/2`, reads ahead
- If WAV reaches EOF and `loop == true`: seek back to `data_offset`, continue
- File handle left open while lane is active; closed on lane stop

### 1.4 Sample rate conversion
- Fixed-point linear interpolation in `wav_read_frames` output stage
- Ratio: `src_sr << 16 / 48000` — precomputed once on lane load
- No malloc, no float; two int32 multiplies per output sample

## Phase 2 — Clock & Lane Engine

### 2.1 Master clock
```c
typedef struct {
    float    bpm;           // 20.0 – 300.0
    uint32_t tick_rate;     // ticks per beat (default 96 PPQN)
    uint32_t tick_count;    // absolute tick since play start
    bool     running;
} clock_t;
```
- Clock advances inside the audio task: every `AUDIO_BUF_FRAMES` samples, increment ticks by `(AUDIO_BUF_FRAMES * tick_rate * bpm) / (60 * 48000)` (fixed-point)
- Tap tempo: average of last 4 tap intervals

### 2.2 Lane model (16 lanes)
```c
#define NUM_LANES 16

typedef enum {
    LANE_TYPE_WAV,        // streams a WAV file from SD (one-shot, no sequencer)
    LANE_TYPE_DRUM,       // one sample per step-sequencer row; multiple samples, grid editor
    LANE_TYPE_SYNTH,      // procedural synth voice(s) with piano roll
} lane_type_t;

typedef struct {
    lane_type_t  type;
    bool         active;
    bool         mute;
    float        volume;        // 0.0 – 1.0
    float        pan;           // -1.0 (L) to +1.0 (R)

    // Clock / loop
    uint32_t     loop_len_ticks; // 0 = no loop (plays once); else repeats every N ticks
    uint32_t     lane_tick;      // current tick within loop

    // WAV source (when type == LANE_TYPE_WAV)
    char         wav_path[128];  // path relative to /sdcard/sounds/
    stream_ring_t *ring;         // allocated in PSRAM

    // Drum sequencer (when type == LANE_TYPE_DRUM)
    drum_seq_t   *drum_seq;      // see Phase 2.5

    // Synth + piano roll (when type == LANE_TYPE_SYNTH)
    synth_inst_t *synth;         // see Phase 3
    piano_roll_t *piano_roll;    // see Phase 2.6

    // Per-lane effect chain (max 4 effects, ordered)
    fx_node_t    fx[4];
    int          fx_count;

    // Internal mixer bus for this lane (written by audio task)
    int32_t      bus_l;
    int32_t      bus_r;
} lane_t;
```

### 2.3 Loop length & restart quantization

Loop length in ticks: user sets in musical units (bars × beats × subdivisions).
Example: 4/4 at 96 PPQN → 1 bar = 384 ticks.
**Per-lane, independently**: lane A can be 2 bars, lane B can be 3 bars — they drift naturally (polyrhythm).
Minimum resolution: 1 tick (~1 ms @ 120 BPM, 96 PPQN).

**Two playback modes — LIVE vs SONG — determine loop restart behavior:**

#### LIVE mode (default when [LIVE] is active)
- Loop restarts **immediately** (`lane_tick = 0`) when `lane_tick >= loop_len_ticks`
- Manual retrigger (tap pad / play button) also restarts immediately with no quantization
- Purpose: live jamming, instant response, finger-drumming feel
- `song_t.playback_mode == PLAYBACK_LIVE`

#### SONG mode (SONG VIEW, composition)
- Loop restarts **snap to the next bar boundary** of the master clock
- When `lane_tick >= loop_len_ticks`: set `lane.pending_restart = true`; actual `lane_tick = 0` only fires when `master_tick % bar_ticks == 0`
- If loop_len_ticks is already a whole number of bars (the common case) this is identical to immediate restart — no audible difference
- Prevents polyrhythm drift when assembling a song; all lanes re-align on bar 1 after their own loop ends
- `song_t.playback_mode == PLAYBACK_SONG`

**Data model additions to `lane_t`:**
```c
bool     pending_restart;   // SONG mode: restart queued, fires on next bar boundary
```

**Data model additions to `song_t`:**
```c
typedef enum { PLAYBACK_LIVE, PLAYBACK_SONG } playback_mode_t;
playback_mode_t playback_mode;   // toggled by [LIVE] button; persisted in .s32 file
```

**Audio tick engine change (section 2.4 step 2 / loop check):**
```c
// LIVE mode
if (lane->lane_tick >= lane->loop_len_ticks) {
    lane->lane_tick = 0;
    // seek WAV / reset synth pattern
}

// SONG mode
if (lane->lane_tick >= lane->loop_len_ticks)
    lane->pending_restart = true;
if (lane->pending_restart && (master_tick % bar_ticks == 0)) {
    lane->pending_restart = false;
    lane->lane_tick = 0;
    // seek WAV / reset synth pattern
}
```

`bar_ticks = ppqn * beats_per_bar` (e.g. 96 × 4 = 384 at 4/4).

### 2.4 Audio mix task (core 1)
```
for each AUDIO_BUF_FRAMES block:
  1. advance master clock ticks
  2. for each lane:
       if lane.mute == true: skip entirely (clock still advances, ADSR still gates)
       a. if WAV: drain stream_ring into lane bus (apply volume, pan)
       b. if DRUM: trigger steps, drain active rings into lane bus
       c. if SYNTH: render synth voices into lane bus
       d. apply ADSR envelope to lane bus
       e. apply per-lane FX chain in order
       f. accumulate lane bus → master bus
  3. apply master FX chain
  4. clip & write to I2S
```
- **Mute behaviour**: when `lane.mute == true` the lane bus contributes zero to the
  master bus. The SD stream task still refills rings (keeps file position current) and
  the clock still advances `lane_tick` (loop stays in sync). Unmuting is instant with
  no click artifact because the bus is simply included again from the next block.
- `lane.mute` is a `volatile bool` — safe to write from the touch/WS task, read from
  the audio task without a mutex (single-byte write is atomic on RISC-V).
- **No heap allocation in this loop** — all buffers pre-allocated at init
- Mix bus: `int32_t` (accumulates without overflow for 16 lanes × 32767)
- Final clip to int16 before I2S write

### 2.5 Drum step sequencer (LANE_TYPE_DRUM)

A drum lane holds up to **16 instrument rows** (each row = one sample/WAV file from SD).
Each row has an independent step grid. All rows share the lane's loop length and subdivision.

```c
#define DRUM_MAX_ROWS     16   // max sample rows per drum lane
#define DRUM_MAX_STEPS    64   // max steps per row (at finest resolution)

typedef struct {
    uint8_t  velocity;   // 0 = off, 1–127 = on with velocity
    bool     accent;     // louder hit (multiplied by accent_gain)
} drum_step_t;

typedef enum {
    SAMPLE_PLAY_ONE_SHOT,    // play to EOF then stop (default)
    SAMPLE_PLAY_LOOP,        // loop between loop_start and loop_end continuously
    SAMPLE_PLAY_LOOP_PING,   // ping-pong: forward then backward between loop points
    SAMPLE_PLAY_GATE,        // play while step is held (for tied steps); stop on note-off
    SAMPLE_PLAY_SLICE,       // play only between slice_start and slice_end, then stop
} sample_play_mode_t;

#define MULTI_HIT_MAX  8   // max chained samples per row

typedef struct {
    char        wav_path[128];              // sample for this row
    stream_ring_t *ring;                    // PSRAM ring, one per active row

    // Playback mode
    sample_play_mode_t play_mode;
    uint32_t    loop_start;     // byte offset into PCM data for loop start point
    uint32_t    loop_end;       // byte offset for loop end (0 = EOF)
    uint32_t    slice_start;    // for SLICE mode: start byte
    uint32_t    slice_end;      // for SLICE mode: end byte

    // Multi-hit: chain of samples fired in quick succession on one trigger
    uint8_t     multi_hit_count;            // 0 or 1 = normal; 2–8 = multi-hit chain
    char        multi_wav[MULTI_HIT_MAX][128]; // paths for hits 2..N (hit 1 = wav_path)
    uint16_t    multi_gap_ms[MULTI_HIT_MAX];   // gap in ms before each successive hit (0 = immediate)
    stream_ring_t *multi_ring[MULTI_HIT_MAX];  // PSRAM rings pre-allocated for each slot
    uint8_t     multi_idx;      // runtime: which hit is currently active
    uint32_t    multi_next_tick;// runtime: tick when next hit fires

    drum_step_t  steps[DRUM_MAX_STEPS];    // the grid
    uint8_t      step_count;
    float        volume;
    float        pan;
    float        pitch;         // semitone detune ±24 (applied via playback rate)
    bool         mute;
    bool         solo;
    bool         reverse;       // play sample backwards
    float        start_offset;  // 0.0–1.0: start position within sample (chop front)
} drum_row_t;

typedef struct {
    drum_row_t  rows[DRUM_MAX_ROWS];
    uint8_t     row_count;         // how many rows are loaded
    uint8_t     step_count;        // 8 / 16 / 32 / 64 — resolution selector
    uint8_t     current_step;      // advances with clock
    float       accent_gain;       // multiplier for accented steps (default 1.5)
} drum_seq_t;
```

**Sample playback modes** (`sample_play_mode_t`):

| Mode | Behaviour | Good for |
|------|-----------|----------|
| ONE_SHOT | Plays from start (or `start_offset`) to EOF, then stops | kick, snare, standard hits |
| LOOP | Loops between `loop_start` and `loop_end` indefinitely until step retriggers or mute | hi-hat buzz, sustained hits, texture layers |
| LOOP_PING | Ping-pong between loop points (forward → backward → forward) | metallic sweeps, smooth loops with no click at boundary |
| GATE | Plays while the step is active; stops when the next step does not retrigger | sustained notes driven by tied steps |
| SLICE | Plays only between `slice_start` and `slice_end` byte offsets, then stops | chop a long sample into addressable regions per row |

Loop points are set in the row editor via a mini waveform view with draggable start/end handles (same approach as the sample cutter). Loop cross-fade (2–8 ms) is applied automatically to prevent clicks.

**Multi-hit** (`multi_hit_count > 1`):

Fire a rapid chain of samples on a single step trigger — each hit can be a different sample or the same sample repeated, with a configurable gap between them. The chain plays through automatically; no extra steps needed.

Examples:
- Flam: `multi_hit_count=2`, same snare sample, `multi_gap_ms[1]=8` → classic drum flam
- Roll: `multi_hit_count=6`, same snare, `multi_gap_ms[1..5]=30` → snare roll in one step
- Layered attack: `multi_hit_count=3`, different transients, gaps 0/5/12 ms → complex layered hit
- Stutter: `multi_hit_count=4`, same sample at different `slice_start` offsets per hit → choppy stutter

Multi-hit fires are scheduled ahead as `multi_next_tick` offsets computed at step trigger time. The audio task checks `multi_next_tick` each block and retriggers the next `multi_ring` in the chain when the tick arrives. All `multi_ring[]` are pre-allocated in PSRAM at lane load — no heap at trigger time.

**Additional per-row parameters:**

| Param | Range | Effect |
|-------|-------|--------|
| `pitch` | ±24 semitones | Shifts playback rate (tune sample up/down) |
| `reverse` | bool | Plays sample backwards (pre-computed reverse in PSRAM ring fill) |
| `start_offset` | 0.0–1.0 | Skip into sample before playing — chop the attack transient |

**Step resolution options** (user-selectable per drum lane):

| Resolution | Steps per bar (4/4) | Step duration | Use case |
|------------|--------------------:|---------------|----------|
| 8  steps   | 8  | 1/8 note  | slow, sparse patterns |
| 16 steps   | 16 | 1/16 note | standard drum machine |
| 32 steps   | 32 | 1/32 note | ghost notes, hip-hop swing |
| 64 steps   | 64 | 1/64 note | very fast fills, micro-timing |

- Resolution can be changed live; steps are re-mapped proportionally (16→32: each step duplicates)
- All rows in a drum lane share the same resolution
- `current_step` advances when `lane_tick % (loop_len_ticks / step_count) == 0`
- On step trigger: WAV ring is rewound to `data_offset` (retrigger), velocity scales amplitude

**Playback in audio task (2.4 step b — drum lane variant)**:
```
for each new step tick:
  for each row r in drum_seq:
    if rows[r].steps[current_step].velocity > 0:
      retrigger ring[r] from start of sample
      set ring[r].gain = velocity/127 * accent_gain_if_accent * row.volume
drain all active rings into lane bus with per-row pan
```

### 2.6 Piano roll (LANE_TYPE_SYNTH)

A synth lane stores notes as a list of timestamped note-on/off events, displayed and edited
as a scrollable piano roll.

```c
#define PIANO_ROLL_MAX_NOTES  256   // per lane — stored in PSRAM

typedef struct {
    uint32_t tick_start;   // tick within loop where note starts
    uint32_t tick_len;     // duration in ticks (0 = note still held / until loop end)
    uint8_t  note;         // MIDI note number 0–127
    uint8_t  velocity;     // 1–127
} pr_note_t;

typedef struct {
    pr_note_t  notes[PIANO_ROLL_MAX_NOTES];  // in PSRAM
    uint16_t   note_count;
    uint8_t    step_resolution;   // snap grid: 4/8/16/32/64 steps per bar
    uint8_t    view_octave;       // topmost visible octave (scroll state)
    uint32_t   view_tick_offset;  // leftmost visible tick (horizontal scroll state)
    uint32_t   view_ticks_wide;   // how many ticks fit in the view (zoom level)
} piano_roll_t;
```

**Note resolution / snap grid** (same options as drum sequencer):
- 4 / 8 / 16 / 32 / 64 steps per bar
- Notes snap to the nearest grid line on placement
- Grid can be disabled for free-form placement

**Playback in audio task (2.4 step b — synth lane variant)**:
```
for each frame:
  for each note n in piano_roll:
    if lane_tick == n.tick_start:  note_on(synth, n.note, n.velocity)
    if lane_tick == n.tick_start + n.tick_len: note_off(synth, n.note)
render synth voices → lane bus
```
- Note events are sorted by `tick_start` at edit time; audio task does a single linear scan per frame
  (at 96 PPQN most frames have 0 events to process)

### Arpeggiator (per SYNTH lane)

Each synth lane has a built-in arpeggiator that operates between the piano roll / live
note-on events and the synth voice engine. When enabled it intercepts held notes and
cycles through them (or a pattern derived from them) automatically in time with the clock.

```c
typedef enum {
    ARP_UP,           // low → high
    ARP_DOWN,         // high → low
    ARP_UP_DOWN,      // low → high → low (no repeat at extremes)
    ARP_UP_DOWN_INCL, // low → high → low (repeats extremes)
    ARP_DOWN_UP,      // high → low → high
    ARP_ORDER,        // note-on order (as played / placed)
    ARP_RANDOM,       // random pick from held notes each step
    ARP_CHORD,        // all held notes fire simultaneously (strum mode)
    ARP_AS_PLAYED,    // replay in exact note-on sequence, with original durations
} arp_mode_t;

typedef struct {
    bool        enabled;
    arp_mode_t  mode;
    uint8_t     octave_range;   // 1–4: cycle spreads notes across N octaves
    uint8_t     step_div;       // clock divisions: 4=1/4, 8=1/8, 16=1/16, 32=1/32
    bool        latch;          // hold notes after finger lifts until new note pressed
    uint8_t     gate_pct;       // note duration as % of step (10–100 %)
    uint8_t     velocity_mode;  // ORIGINAL=use note velocity; ACCENT=alternate; FIXED=constant
    uint8_t     fixed_vel;      // velocity when velocity_mode=FIXED
    bool        retrigger;      // retrigger envelope on each arp step
    uint8_t     swing_pct;      // 50 = straight, 51–75 = swing (delay even steps)

    // runtime state
    uint8_t     held[16];       // held MIDI notes, insertion order
    uint8_t     held_count;
    uint8_t     seq[32];        // computed arp sequence from held notes + mode + octave_range
    uint8_t     seq_len;
    uint8_t     step;           // current position in seq[]
    uint32_t    next_tick;      // clock tick of next arp step
} arp_t;
```

**Arpeggiator modes in detail:**

| Mode | Behaviour | Good for |
|------|-----------|----------|
| UP | C3 E3 G3 C4 E4 G4 (ascending across octave_range) | classic house/trance arps |
| DOWN | G4 E4 C4 G3 E3 C3 | darker feel |
| UP_DOWN | C3 E3 G3 C4 G3 E3 (no repeat at top) | evolving pads |
| UP_DOWN_INCL | C3 E3 G3 C4 G3 E3 C3 (repeats C4) | bouncy |
| ORDER | fires in note-on order regardless of pitch | tap in custom patterns |
| RANDOM | random each step, never silences | chaotic textures |
| CHORD | all notes at once → strummed with tiny delay between each | guitar strum feel |
| AS_PLAYED | replays the exact sequence as placed in piano roll | quantised performance replay |

**Octave range**: octave_range=1 stays in original octave; 2 adds the notes one octave up; 3 adds two octaves up; 4 adds three. Total sequence length = held_count × octave_range.

**Latch**: when enabled, releasing all fingers keeps the current held set playing. New note-on clears the latch and starts a fresh set.

**Swing**: delays every even-numbered arp step by `(step_duration * (swing_pct - 50) / 50)` ticks. At swing_pct=50 all steps are straight.

**Integration with piano roll**: when arp is enabled and the lane has piano roll notes, the piano roll notes act as the "held" set — the arp fires them in sequence rather than playing them as written. When arp is disabled the piano roll plays normally.

**UI**: arp panel in SYNTH LANE DETAIL (below piano roll), also accessible from web UI lane panel. Parameters: mode selector, octave range 1–4, step division, gate %, swing %, latch toggle, velocity mode.

### LFOs (shared, 4 per lane)
- Shape: sine / triangle / square / saw / sample-and-hold
- Destinations: pitch, amplitude, filter cutoff, pan, arp step division, FX param
- Rate: Hz or sync to clock (1/4, 1/8, 1/16, 1/32 …)
- All integer math: LFO phase is uint32_t, shape lookup in 256-entry table
- LFO can modulate arp rate for evolving patterns

### Modulation matrix (per lane)
- 4 sources (LFO1-4) × 8 destinations × depth float
- Sources also include: velocity, note number, ADSR envelope output, random
- Evaluated once per audio block (not per sample) to save CPU

### 4.1 Effect node
```c
typedef enum {
    // Dynamics
    FX_COMPRESSOR,          // RMS compressor
    FX_LIMITER,             // brick-wall limiter (master chain essential)

    FX_FILTER_HP,           // high-pass biquad

    FX_EQ5,                 // 5-band parametric EQ

    // Distortion / saturation
    FX_DISTORTION,          // drive + tone; selectable soft/hard/tube/fuzz modes
    FX_OVERDRIVE,           // soft asymmetric clip (warm, amp-style)
    FX_WAVEFOLD,            // wavefolder — folds signal back on itself (metallic/harsh)
    FX_BITCRUSH,            // bit-depth + sample-rate reducer

    // Time / space
    FX_DELAY,               // stereo delay, clock-syncable

    FX_TREMOLO,             // LFO amplitude modulation
    FX_VIBRATO,             // LFO pitch modulation (delay-line based)

    FX_PAN_AUTO,            // LFO auto-pan left↔right

typedef struct {
```

### 4.2 Per-lane ADSR volume envelope

> **v2 Design (FX+ADSR screen):** Mini top bar: back | "FX · {lane name}" | ADD button.
> **ADSR panel** (top area, `--bg-2` background, 2 px `--line-2` border, 10 px radius):
>   - "LANE ADSR" label in 16 px lime mono + 4 knobs (A/D/S/R, 80 px diameter) side by side.
>   - Mini ADSR preview SVG curve (200×60 px) to the left of the knobs showing current shape with lime fill.
> **FX chain** (middle): 6 slots in a row with arrow chevrons between them. Slot: flex-1 wide × 80 px tall.
>   Filled: `--bg-3` border, slot number 13 px `--t3`, name 22 px bold. Empty: dashed border.
>   Selected: lime border + `--lime-dim` background, name in lime.
> **Selected FX params panel** (bottom, `--bg-2` border box): section header with FX name + "● ON" indicator.
>   Knob row centered: one 80 px knob per parameter, with label (14 px mono `--t2`) and value (20 px mono).

Every lane (WAV, DRUM, SYNTH) has a dedicated ADSR volume envelope independent of any
synth-level ADSR. This shapes the overall amplitude of the lane output over time and can
be used to fade in pads, punch kicks, or gate loops.

```c
typedef struct {
    float attack_ms;    // 0.1 – 10000 ms
    float decay_ms;     // 0.1 – 10000 ms
    float sustain;      // 0.0 – 1.0
    float release_ms;   // 0.1 – 20000 ms

    // runtime state (in PSRAM)
    adsr_stage_t stage; // IDLE/ATTACK/DECAY/SUSTAIN/RELEASE
    float        level; // current envelope amplitude 0.0–1.0
    float        rate;  // samples per stage step (precomputed)
    bool         gate;  // true while lane is playing/held
} lane_adsr_t;
```

- Gate opens when lane starts playing, closes when lane is stopped/muted
- For WAV lanes: gate = sample playing; closes at EOF if loop=off
- For DRUM lanes: each row trigger fires its own micro-ADSR (inside drum_seq_t);
  the lane ADSR is a global envelope over the whole drum mix
- For SYNTH lanes: lane ADSR is separate from per-note synth ADSR; they multiply
- Envelope computed once per audio block (not per sample) — negligible CPU cost
- UI: 4 knobs shown in lane detail view and in the web UI lane panel
- Applied after per-lane FX chain, before master bus accumulation:
  `lane_bus *= lane_adsr.level`

### 4.3 Per-lane effects (per-lane FX chain, max 6 in series)

ADSR is always present and is not a chain slot — see section 4.2. All FX slots below.

#### Dynamics

| Effect | Algorithm | Params | State (PSRAM) |
|--------|-----------|--------|---------------|
| **Compressor** | RMS detector + gain computer, runs at block rate | threshold dBFS, ratio, attack ms, release ms, makeup gain dB | ~64 B |
| **Limiter** | Lookahead brick-wall; 2 ms lookahead delay | ceiling dBFS, release ms | ~4 KB (lookahead buffer) |
| **Gate** | RMS threshold gate with hysteresis | threshold dBFS, attack ms, hold ms, release ms | ~32 B |
| **Transient Shaper** | Independent fast/slow envelope follower difference | attack gain dB (+/-), sustain gain dB (+/-) | ~64 B |

#### Filters & EQ

| Effect | Algorithm | Params | State (PSRAM) |
|--------|-----------|--------|---------------|
| **Filter LP** | 2-pole biquad (Chamberlin SVF), 12 dB/oct | cutoff 20–20k Hz, resonance Q 0.5–20 | 16 B |
| **Filter HP** | Same | cutoff, Q | 16 B |
| **Filter BP** | Same | cutoff, Q | 16 B |
| **Filter Notch** | Band-reject biquad | cutoff, Q | 16 B |
| **EQ 3-band** | Low shelf + mid peak + high shelf, all biquad | low freq/gain, mid freq/Q/gain, high freq/gain | 48 B |
| **EQ 5-band** | 5 fully parametric bands, each biquad | per band: freq, Q, gain dB; global bypass | 80 B |

#### Distortion & Saturation

| Effect | Algorithm | Params | State (PSRAM) | Notes |
|--------|-----------|--------|---------------|-------|
| **Distortion** | Selectable waveshaper: soft-clip (polynomial `x - x³/3`), hard-clip, tube (`tanh`), fuzz (full-wave rect) | drive 0–100, tone (HP before clip, LP after), mode, wet | ~32 B | Good on synth leads, bass |
| **Overdrive** | Asymmetric soft-clip — positive half `tanh`, negative half cubic; adds even harmonics | drive, level | ~16 B | Warm amp character; good on bass/chords |
| **Wavefolder** | Clips signal then mirrors it back inward repeatedly; Buchla-style | fold depth, symmetry | ~16 B | Metallic, bell-like overtones; excellent on pads |
| **Bit-Crush** | Quantise to N bits (1–16), then downsample by integer factor M | bit depth 1–16, sample rate divider 1–32 | ~16 B | Lo-fi, game sounds, glitch |

#### Time & Space

| Effect | Algorithm | Params | State (PSRAM) |
|--------|-----------|--------|---------------|
| **Delay** | Stereo circular buffer in PSRAM, ping-pong option | time ms or clock-sync (1/16–4 bars), feedback 0–0.95, ping-pong on/off, wet | 768 KB (2 sec stereo) |
| **Reverb** | Freeverb: 8 comb + 4 all-pass filters | room size, damping, wet, stereo width | ~32 KB |
| **Chorus** | 3-tap delay (25–35 ms) modulated by sine LFO; summed | rate Hz, depth ms, wet | ~12 KB |
| **Flanger** | 1-tap short delay (1–15 ms) + LFO + feedback | rate Hz, depth, feedback, wet | ~6 KB |
| **Phaser** | 4-stage all-pass chain, LFO sweeps notch frequency | rate Hz, depth, feedback, wet | ~64 B |

#### Modulation

| Effect | Algorithm | Params | State (PSRAM) |
|--------|-----------|--------|---------------|
| **Tremolo** | LFO multiplied onto amplitude | rate Hz (0.1–20), depth, LFO shape (sine/square/saw) | ~32 B |
| **Vibrato** | LFO-modulated short delay line (pitch wobble) | rate Hz, depth semitones (0–2) | ~2 KB |
| **Ring Modulator** | Sample × sine carrier oscillator; creates sum/difference sidebands | carrier freq Hz (1–5000), wet | ~16 B |
| **Pitch Shift** | Granular pitch shift, no time-stretch; suitable for static or slow signals | semitones ±24, grain size ms | ~32 KB |

#### Utility

| Effect | Algorithm | Params | State (PSRAM) |
|--------|-----------|--------|---------------|
| **Auto-Pan** | LFO sweeps pan position L↔R | rate Hz, depth, LFO shape | ~16 B |
| **Stereo Width** | Mid/side encode → scale sides → decode | width 0–200% (0=mono, 100=unchanged, 200=max) | ~16 B |

### 4.4 Master effects chain (max 6 in series)
- Same `fx_node_t` type; operates on master bus after all lanes are mixed
- Master bus: `int32_t[AUDIO_BUF_FRAMES * 2]` in PSRAM — allocated once
- All per-lane effects are available on master too
- Typical master chain: `EQ5 → Compressor → Stereo Width → Limiter`
- Limiter should always be the last slot to prevent digital clipping before I2S write

### 4.5 Effect routing
```
Lane 0  render → [ADSR] → [FX0]→[FX1]→[FX2]→[FX3]→[FX4]→[FX5] → [vol/pan] → master bus
Lane 1  render → [ADSR] → [FX0]→[FX1]                            → [vol/pan] → master bus
...
Lane 15 render → [ADSR] →                                         → [vol/pan] → master bus
Master bus → [MFX0]→[MFX1]→[MFX2]→[MFX3]→[MFX4]→[MFX5] → I2S
                                                            |
                                                   WebSocket audio stream
                                                   (to connected mobile clients)
```
- ADSR applied to lane output before FX chain
- Volume and pan applied after FX chain, before master bus accumulation
- Mute zeros the lane bus without touching ADSR or FX state
- Web stream taps the master bus output (post master-FX) before I2S write

### 5.0 What is a "bar"?

A **bar** (also called a measure) is a fixed number of beats defined by the time signature.
In 4/4 time (the default): 1 bar = 4 beats. At 120 BPM, 1 bar = 2 seconds.
At 96 PPQN: 1 bar = 384 ticks. Loop lengths are always expressed in whole bars:
1 bar, 2 bars, 3 bars, 4 bars, 6, 8, 16, 32. This is the unit displayed everywhere in the UI.

### 5b.3 Save logic
- `song_save(path)`: serialise current `song_t` → JSON → write to SD atomically
  (write to `<path>.tmp`, then `rename()` — avoids corrupt file on power loss)
- `song_load(path)`: parse JSON → populate `song_t` → reload all lane engines
  - Missing WAV files: lane loads but shows "MISSING" warning; audio is silence for that row
  - Unknown synth type: lane loads with type 0 fallback
- **Auto-save**: write `<name>.s32` whenever user leaves SONG VIEW or taps [SAVE SONG]
- **Dirty flag**: shown in top bar as `MySong.s32 *` when unsaved changes exist

## Phase 6 -- Memory Budget Plan

32 MB PSRAM removes all previous constraints. All audio buffers, stream rings, delay lines,
reverb instances, web streaming buffers, and the full web UI asset cache fit comfortably.

| Component | Location | Size |
|-----------|----------|------|
| 3x RGB565 framebuffers (720x1280 x 2B) | PSRAM | ~5.25 MB |
| 16 lanes x 16 drum rows x stream_ring_t (1 KB each) | PSRAM | 256 KB |
| 16x drum_seq_t (16 rows x 64 steps x 2B) | PSRAM | 32 KB |
| 16x piano_roll_t (512 notes x 10B each, expanded) | PSRAM | 80 KB |
| Delay buffers (16 lanes, full 2-sec stereo = 768 KB each) | PSRAM | 12 MB |
| Reverb state (16 active, 32 KB each) | PSRAM | 512 KB |
| ADSR state (16 lanes x 5 voices x 32B each) | PSRAM | ~2.5 KB |
| Audio stream encode ring (1 client, 8 KB) | PSRAM | 8 KB |
| Web UI static assets (HTML/JS/CSS, gzip-compressed) | PSRAM on boot | ~256 KB |
| Master mix bus (1024 frames x 8B) | PSRAM | 8 KB |
| WebSocket message queue (per client, 4 KB each, 4 clients) | PSRAM | 16 KB |
| Synth voice state (20 types x 5 voices x ~128B) | SRAM | ~12.5 KB |
| Audio output buffer (512 frames x 4B) | SRAM (DMA-capable) | 4 KB |
| FX biquad state | SRAM | < 1 KB |
| SD file handles (16 open max) | SRAM | < 4 KB |
| **Total PSRAM used** | | **~18.5 MB of 32 MB** |
| **Total SRAM used** | | **~30 KB** |
| **PSRAM headroom** | | **~13.5 MB free** |

No mitigations required. All 16 delay lines at 2 sec, all 16 reverbs active, single
audio stream client — all run simultaneously with room to spare.

## Phase 8 -- WebSocket Control Protocol

All UI actions that can be performed on the touchscreen can also be performed from a
connected browser. The device runs a WebSocket server alongside the existing HTTP server.
The web UI is a single-page app served from PSRAM (gzip-compressed at build time).

### 8.1 WebSocket server

- Endpoint: `ws://synth-32.local/ws` (also reachable as `ws://192.168.4.1/ws`)
- Max simultaneous control clients: 4 (one semaphore per slot)
- Protocol: binary frames, first byte = message type, rest = payload
- All messages are bidirectional; device sends state diffs to clients on any change
  (whether triggered by touch, web client, or internal clock)

```c
typedef enum {
    // Device -> Client (state updates)
    WS_MSG_FULL_STATE    = 0x01,  // full song_t dump on connect
    WS_MSG_LANE_UPDATE   = 0x02,  // one lane changed (vol, pan, mute, type, name)
    WS_MSG_DRUM_STEP     = 0x03,  // one drum step toggled
    WS_MSG_NOTE_EVENT    = 0x04,  // piano roll note added/removed
    WS_MSG_FX_UPDATE     = 0x05,  // FX param changed (lane or master)
    WS_MSG_ADSR_UPDATE   = 0x06,  // ADSR param changed for a lane
    WS_MSG_CLOCK_UPDATE  = 0x07,  // BPM/PPQN/time sig changed
    WS_MSG_TRANSPORT     = 0x08,  // play/stop state
    WS_MSG_MASTER_UPDATE = 0x09,  // master vol/pan/FX
    WS_MSG_SONG_LIST     = 0x0A,  // list of songs on SD
    WS_MSG_SETTINGS      = 0x0B,  // current settings
    WS_MSG_METER         = 0x0C,  // L/R peak+RMS levels (sent 10x/sec)
    WS_MSG_PLAYHEAD      = 0x0D,  // current tick + per-lane step position (sent 25x/sec)
    WS_MSG_SYNTH_PARAMS  = 0x0E,  // all params for one synth

    // Client -> Device (commands)
    WS_CMD_SET_LANE      = 0x80,  // set lane fields (vol, pan, mute, name, loop_bars)
    WS_CMD_TOGGLE_MUTE   = 0x95,  // toggle lane.mute by index — single-byte payload (lane_idx)
    WS_CMD_SET_DRUM_STEP = 0x81,  // set one step (lane, row, step, velocity, accent)
    WS_CMD_ADD_NOTE      = 0x82,  // add piano roll note
    WS_CMD_DEL_NOTE      = 0x83,  // delete piano roll note
    WS_CMD_SET_FX        = 0x84,  // set FX slot in lane or master chain
    WS_CMD_SET_ADSR      = 0x85,  // set lane ADSR params
    WS_CMD_SET_CLOCK     = 0x86,  // set BPM/PPQN/time sig
    WS_CMD_TRANSPORT     = 0x87,  // play / stop / tap-tempo
    WS_CMD_SET_MASTER    = 0x88,  // set master vol/pan
    WS_CMD_SAVE_SONG     = 0x89,  // trigger save (with optional name)
    WS_CMD_LOAD_SONG     = 0x8A,  // load song by filename
    WS_CMD_NEW_SONG      = 0x8B,  // new song
    WS_CMD_LIST_SONGS    = 0x8C,  // request song list
    WS_CMD_SET_SETTINGS  = 0x8D,  // update settings
    WS_CMD_ADD_LANE      = 0x8E,  // add a new lane (type + defaults)
    WS_CMD_DEL_LANE      = 0x8F,  // delete lane by index
    WS_CMD_DRUM_ROW_ASSIGN = 0x90, // assign WAV to drum row
    WS_CMD_SET_SYNTH     = 0x91,  // set synth type + params
    WS_CMD_NOTE_ON       = 0x92,  // live play: note on (from web piano)
    WS_CMD_NOTE_OFF      = 0x93,  // live play: note off
    WS_CMD_DRUM_TRIGGER  = 0x94,  // live play: trigger drum pad
    WS_CMD_AUDIO_STREAM  = 0xF0,  // request audio stream on/off for this client
} ws_msg_type_t;
```

### 8.2 State sync model

**Architecture: the web UI is an additional remote GUI over the data. It does not control
the device -- it changes the data, and the device (touch screen + audio engine) reacts to
that data change exactly as it would if the touch screen had made the same change.**

```
Touch screen (device)          Web browser (phone/desktop)
     |                                |
     | directly reads/writes          | sends WS_CMD_* binary frame
     | song_t, lane_t, drum_seq_t     |         |
     |                                |         v
     +----------> song_t  <-----------+   ws_cmd_dispatch()
                  lane_t                  writes into same structs
                  drum_seq_t
                  piano_roll_t
                     |
                     | on any field change (from touch OR from WS dispatch):
                     v
              ws_broadcast_diff()  -->  all connected WS clients get WS_MSG_*
                                        (browser redraws its canvas to match)
```

**How changes flow:**

- **Touch UI** (device screen): directly mutates `song_t` / `lane_t` / `drum_seq_t` fields.
  After writing, calls `ws_notify_change(WS_MSG_LANE_UPDATE, lane_idx)` which triggers a
  broadcast to all WS clients. The touch UI does NOT go through a command queue --
  it is the primary, zero-latency interface.

- **Web UI** (browser): sends a `WS_CMD_*` binary frame over WebSocket.
  `ws_cmd_dispatch()` on the device decodes the frame and writes the same fields in
  `song_t` / `lane_t` / `drum_seq_t` that the touch UI would have written directly.
  Then calls the same `ws_notify_change()`. The web UI never talks to the audio engine
  or touch UI directly -- it only changes the shared data.

- **Device screen reacts**: the touch UI render loop reads `song_t` every frame.
  When a web client changes BPM, the BPM field in `song_t` is updated; next time the
  touch screen redraws its top bar, it shows the new value. The device screen does not
  receive "push notifications" from the WS layer -- it simply re-reads live data.

- **Audio engine reacts**: the audio task reads `song_t` / `lane_t` fields directly
  (they are `volatile` where needed). When the web changes a drum step, the next audio
  block sees the updated step grid automatically.

```c
// No command queue between touch and WS.
// Both touch and WS write directly to the shared data structs.

// Called by touch UI after any direct mutation:
void ws_notify_change(ws_msg_type_t diff_type, int lane_idx);

// Called by WebSocket receive task to apply a web command to the data:
void ws_cmd_dispatch(const uint8_t *frame, size_t len);
// ws_cmd_dispatch writes fields then calls ws_notify_change internally.

// ws_notify_change serialises the affected struct and broadcasts to all clients:
void ws_notify_change(ws_msg_type_t type, int idx) {
    uint8_t buf[256];
    size_t  len = ws_serialise_diff(type, idx, buf);
    for (int i = 0; i < WS_MAX_CLIENTS; i++) {
        if (s_clients[i].active)
            httpd_ws_send_frame_async(s_clients[i].fd, buf, len);
    }
}
```

**Result:**
- Touch screen changes BPM -> `song.bpm` updated -> broadcast -> browser shows new BPM
- Browser changes BPM -> `ws_cmd_dispatch` writes `song.bpm` -> broadcast -> touch screen
  redraws top bar with new value on its next render tick (≤16 ms)
- Both always show the same data because both read/write the same structs
- No merge logic, no conflict resolution, no state machines -- just shared memory

### 8.3 Audio streaming over WebSocket

**Single audio client at a time.** When a client sends `WS_CMD_AUDIO_STREAM enable=1`:

1. If another client currently holds the audio stream, drop it immediately: free its encode ring, clear its audio flag, send it `WS_MSG_AUDIO_DROPPED` so it can update its UI.
2. Allocate a single 8 KB encode ring in PSRAM for the new client.
3. After each I2S audio block is written, copy the `int16_t` stereo samples into the ring.
4. A dedicated `ws_audio_task` (core 0, priority 8) drains the ring and sends:
   - **Format**: 16-bit PCM, stereo, 48 kHz, little-endian, raw binary (no container)
   - **Frame size**: 256 frames = 1024 bytes per WebSocket binary frame
   - **Latency contribution**: ~5.3 ms per frame at 48 kHz — small packets reduce WiFi jitter impact on mobile Web Audio scheduling
   - No compression — PCM first; Opus only if WiFi proves lossy in practice
   - Bandwidth: 48000 × 2ch × 2B = ~1.5 Mbps (single client, within AP limit)

Add to `ws_msg_type_t`:
```c
WS_MSG_AUDIO_DROPPED = 0x0F,  // server dropped this client's audio stream (new client took it)
```

**Device speaker mute while audio client is active:**
```c
// In audio task, after I2S write:
if (s_audio_client_fd >= 0) {
    gpio_set_level(GPIO_PA, 0);  // mute PA — phone is the speaker
    // copy block into encode ring
} else {
    gpio_set_level(GPIO_PA, 1);  // PA on — no wireless listener
}
```
- `s_audio_client_fd`: fd of the single active audio client, or -1 if none
- PA re-enabled immediately when client disconnects or sends `enable=0`
- All controls, touch UI, and other WS clients remain fully responsive

**Client-side (Web Audio API, JS):**
```js
// Receive binary PCM frames and schedule them gap-free
const SAMPLE_RATE = 48000;
const SCHED_AHEAD_S = 0.10;  // 100 ms scheduling buffer — tune down to ~50 ms if mobile is stable
let nextPlayAt = 0;

ws.onmessage = (e) => {
    if (!(e.data instanceof ArrayBuffer)) return;
    const pcm = new Int16Array(e.data);          // 256 stereo frames = 512 int16 values
    const frames = pcm.length / 2;
    const buf = audioCtx.createBuffer(2, frames, SAMPLE_RATE);
    const L = buf.getChannelData(0), R = buf.getChannelData(1);
    for (let i = 0; i < frames; i++) {
        L[i] = pcm[i * 2]     / 32768;
        R[i] = pcm[i * 2 + 1] / 32768;
    }
    const src = audioCtx.createBufferSource();
    src.buffer = buf;
    src.connect(audioCtx.destination);
    const now = audioCtx.currentTime;
    if (nextPlayAt < now + 0.005) nextPlayAt = now + 0.005;  // resync if we fell behind
    src.start(nextPlayAt);
    nextPlayAt += frames / SAMPLE_RATE;
};
```

### 8.4 WebSocket server implementation

- Use `esp_http_server` WebSocket support (available in IDF 5.x, the P4's SDK version)
- `httpd_ws_recv_frame` / `httpd_ws_send_frame` for frame I/O
- Each client connection gets a `ws_client_t` slot with:
  - Socket file descriptor
  - Audio stream ring (PSRAM, allocated on `WS_CMD_AUDIO_STREAM enable=1`)
  - Last-sent state version (for diff suppression)
- Broadcast helper: `ws_broadcast(msg, len)` iterates all active slots

## Phase 9 -- Web UI (Browser-Side)

The web UI is a single HTML file with embedded JavaScript and CSS, served via HTTP GET `/`
from the device. It is gzip-compressed and stored in a C array in PSRAM at boot
(generated by `tools/build_web.py` which runs before the IDF build).

### 9.1 Core principle: canvas-first, WebSocket-only, zero HTTP after load

- **All rendering uses `<canvas>`** -- every screen that uses canvas on the device
  (drum grid, piano roll, live play piano keys, level meters) uses an identical canvas
  implementation in the browser. Same cell sizes, same color palette (RGB565 values
  converted to CSS hex), same layout proportions. The goal is that a screenshot of the
  web UI and a screenshot of the device UI are visually indistinguishable.
- **The web UI is an additional GUI over the shared data -- not a controller of the device.**
  The browser does not control the audio engine or the touch screen. It changes the same
  data structs (`song_t`, `lane_t`, `drum_seq_t`) that the touch screen reads directly.
  The device touch screen and audio engine simply react to those data changes as they
  would to any other change -- they are not "notified" by the web, they just see new values.
- **All user actions send a WebSocket binary frame immediately** -- no HTTP requests
  after the initial page load. Every button click, slider drag, step toggle, note place,
  mute toggle sends a `WS_CMD_*` binary frame on the existing WebSocket connection.
  Round-trip is typically <5 ms on the local AP.
- **No optimistic UI updates** -- the browser JS state object is never mutated directly
  on user action. The frame is sent; the device writes the data; the device broadcasts
  `WS_MSG_*` back to all clients; the `onmessage` handler updates the JS state and
  redraws. Because the device includes the sender in its broadcast, feedback arrives in
  the same <5 ms -- imperceptible. This means the browser canvas always shows exactly
  what the device data contains, no more and no less.
- **Device touch screen reacts to data changes automatically** -- the touch render loop
  reads `song_t` every frame. When a web client changes BPM, the device top bar shows
  the new value on its next render tick without any explicit notification pathway.
- **No framework dependencies** -- vanilla JS + CSS only; must work offline (device is AP)
- **No build step required at runtime** -- single self-contained HTML file
- Minified + gzip: target < 200 KB compressed

### 9.2 Web UI screen tree (mirrors device 5.1 exactly)

### 9.3 Drum grid canvas (web) -- mirrors device 5.3 exactly

**Canvas layout**: identical pixel math to the device gfx implementation.
Cell width = `(canvas.width - ROW_LABEL_W - VOL_W) / step_count`.
Cell height = `(canvas.height - HEADER_H - FOOTER_H) / row_count`.
Same constants as the device `ui_drum_editor.c`.

**Rendering** (called on every `WS_MSG_*` that affects drum state, and on `WS_MSG_PLAYHEAD`):
```javascript
function drawDrumGrid(ctx, seq, playhead_step) {
    // background
    ctx.fillStyle = '#111';
    ctx.fillRect(0, 0, canvas.width, canvas.height);

    for (let r = 0; r < seq.rows.length; r++) {
        for (let s = 0; s < seq.step_count; s++) {
            const step = seq.rows[r].steps[s];
            const x = ROW_LABEL_W + VOL_W + s * cellW;
            const y = HEADER_H + r * cellH;
            // same color logic as device:
            if (s === playhead_step)      ctx.fillStyle = '#2a2a2a'; // playhead col tint
            else if (step.v === 0)        ctx.fillStyle = '#222222'; // off
            else if (step.accent)         ctx.fillStyle = '#FFD700'; // accented
            else                          ctx.fillStyle = '#00FF00'; // on
            ctx.fillRect(x+1, y+1, cellW-2, cellH-2);
        }
        // row label, vol bar -- same widths as device
    }
    // playhead vertical line
    const phx = ROW_LABEL_W + VOL_W + playhead_step * cellW;
    ctx.fillStyle = 'rgba(255,255,255,0.15)';
    ctx.fillRect(phx, HEADER_H, cellW, seq.rows.length * cellH);
}
```

**All interactions send WS binary frames immediately, no local state mutation:**
- `mousedown` on step cell -> send `WS_CMD_SET_DRUM_STEP` (lane, row, step, toggle velocity)
- `contextmenu` on step cell -> show velocity `<input range>` overlay; `input` event sends
  `WS_CMD_SET_DRUM_STEP` with new velocity on each change (live preview on device)
- `dblclick` on step cell -> send `WS_CMD_SET_DRUM_STEP` with accent flag toggled
- Resolution `<select>` change -> send `WS_CMD_SET_LANE` with new step_count
- Loop length `<select>` change -> send `WS_CMD_SET_LANE` with new loop_bars
- Row label `dblclick` -> inline `<input>` edit; `blur` sends `WS_CMD_SET_LANE` row name
- Mute checkbox -> send `WS_CMD_TOGGLE_MUTE`; row dims immediately on `WS_MSG_LANE_UPDATE`
- `[assign sound]` button -> open sound browser panel (9.8); selection sends
  `WS_CMD_DRUM_ROW_ASSIGN`
- Row vol slider (`mousedown`+`mousemove`) -> send `WS_CMD_SET_LANE` row volume on each move

**Playhead animation**: `WS_MSG_PLAYHEAD` arrives 25x/sec. On each message, call
`drawDrumGrid()` -- no `requestAnimationFrame` loop needed; the WS message IS the clock.

### 9.4 Piano roll canvas (web) -- mirrors device 5.4 exactly

**Canvas layout**: identical to device `ui_piano_roll.c`.
- Left column: piano keys, width = `KEY_W` (48 px, same as device)
- Remaining width: note grid, horizontal = time (ticks), vertical = pitch (semitones)
- `ticksPerPx = view_ticks_wide / (canvas.width - KEY_W)` -- same zoom formula as device
- Row height per semitone = `NOTE_H` (12 px, same as device)
- Black key rows: background `#1a1a1a`; white key rows: background `#111111`
- Same colors as device: note = `#00FF00`, selected = white outline, velocity brightness

**Rendering**:
```javascript
function drawPianoRoll(ctx, roll, playhead_tick) {
    // grid background -- same as device
    for (let note = 0; note < 128; note++) {
        const y = noteToY(note);  // same formula as device
        ctx.fillStyle = isBlackKey(note) ? '#1a1a1a' : '#111111';
        ctx.fillRect(KEY_W, y, canvas.width - KEY_W, NOTE_H - 1);
    }
    // bar/beat grid lines -- same spacing as device
    drawGridLines(ctx, roll.view_tick_offset, roll.view_ticks_wide);
    // notes
    for (const n of roll.notes) {
        const x = KEY_W + tickToX(n.tick);
        const y = noteToY(n.note);
        const w = Math.max(2, tickToX(n.tick + n.len) - tickToX(n.tick));
        const brightness = Math.floor(64 + (n.vel / 127) * 191); // velocity -> brightness
        ctx.fillStyle = `rgb(0,${brightness},0)`;
        ctx.fillRect(x, y + 1, w - 1, NOTE_H - 2);
    }
    // playhead
    const phx = KEY_W + tickToX(playhead_tick - roll.view_tick_offset);
    ctx.fillStyle = 'rgba(255,255,255,0.6)';
    ctx.fillRect(phx, 0, 1, canvas.height);
    // piano keys -- same white/black key drawing as device
    drawPianoKeys(ctx);
}
```

**All interactions send WS binary frames immediately:**
- `mousedown` on empty grid area -> compute tick+note from pixel (same formula as device),

### 9.9 WebSocket message discipline

The web UI is a remote view of the device's data. The flow for every user interaction:

```
Browser (phone/desktop)              Device (ESP32-P4)
                                      song_t / lane_t / drum_seq_t
                                      (shared data -- lives in PSRAM)
                                             ^
user taps drum step                          |  touch screen also reads/writes here directly
    |                                        |
    v                                        |
build WS_CMD_SET_DRUM_STEP frame             |
ws.send(frame)  -----> ws_cmd_dispatch() writes step into drum_seq_t
                                             |
                                        ws_notify_change()
                                             |
                        <-- WS_MSG_* broadcast to ALL clients (incl. sender)
                                             |
                             +---------------+-------------------+
                             v                                   v
                    browser onmessage:                  touch screen render loop:
                    update JS state copy                reads drum_seq_t directly,
                    redraw drum grid canvas             sees new step on next frame
```

Rules:
- The browser JS state is a **read-only mirror** of device data, updated only by
  incoming `WS_MSG_*` frames -- never by the user's own action directly
- The device touch screen reads data directly from memory -- it does not receive
  "push events" from the WS layer; it sees changes because it reads the same structs
- Latency browser -> visible on browser canvas: WS round-trip ~3-8 ms on local AP
- Latency browser -> visible on device screen: same ~3-8 ms WS + ≤16 ms render tick

**Binary frame format** (same as Phase 8.1):
```javascript
function buildCmd(type, payload_bytes) {
    const buf = new Uint8Array(1 + payload_bytes.length);
    buf[0] = type;
    buf.set(payload_bytes, 1);
    return buf.buffer;
}
```

### 9.6 Audio playback in browser (received stream)

When user clicks [AUDIO ON] in the web UI:
1. Browser sends `WS_CMD_AUDIO_STREAM enable=1`
2. Device starts sending binary WebSocket frames (raw PCM 16-bit stereo 48 kHz)
3. Browser decodes via Web Audio API:

```javascript
const ctx = new AudioContext({ sampleRate: 48000 });
const FRAMES = 512;
const CHANNELS = 2;

ws.onmessage = (evt) => {
    if (!(evt.data instanceof ArrayBuffer)) return;
    const pcm = new Int16Array(evt.data);
    const buf = ctx.createBuffer(CHANNELS, FRAMES, 48000);
    for (let c = 0; c < CHANNELS; c++) {
        const ch = buf.getChannelData(c);
        for (let i = 0; i < FRAMES; i++) {
            ch[i] = pcm[i * CHANNELS + c] / 32768.0;
        }
    }
    const src = ctx.createBufferSource();
    src.buffer = buf;
    src.connect(ctx.destination);
    // Schedule back-to-back for gapless playback
    src.start(nextTime);
    nextTime += buf.duration;
};
```
- `nextTime` starts at `ctx.currentTime + 0.1` (100 ms buffer to absorb WiFi jitter)
- If a frame arrives late: schedule immediately (`Math.max(nextTime, ctx.currentTime + 0.02)`)
- [AUDIO ON] button toggles; on click: device speaker mutes, stream starts
- [AUDIO OFF] or tab close: sends `WS_CMD_AUDIO_STREAM enable=0`; device speaker re-enables

### 9.7 Build pipeline for web assets

```

  web/
```

3. gzip compress
4. Write C array: `const uint8_t WEB_HTML_GZ[] = { 0x1f, 0x8b, ... };`

### 9.8 Sample cutter (web tool)

A dedicated screen in the web UI for cutting regions out of a WAV file already on the SD
card and saving each cut as a new individual WAV in a named folder on the SD card.
Accessible from MENU → SAMPLE CUTTER.

**Use case**: you have a long audio file (a drum loop, a recorded jam, a field recording)
on the SD card and want to slice it into individual one-shots or loops.

**Screen layout:**

```
+-- SAMPLE CUTTER ------------------------------------------+
|  Source:  [sounds/MyKit/loop.wav          ] [BROWSE]       |
|  Save to: [sounds/MyKit-cuts/             ] [NEW FOLDER]   |
+-----------------------------------------------------------+
|                                                           |
|  [PLAY]  [STOP]  ◄ 0:00.000          1:23.456 ►          |
|                                                           |
|  ████████████████████████████████████████████████████     |
|  ▲ waveform (canvas, full file width, zoomable)           |
|  |                                                        |
|  ├──[  ]────────────[  ]──  region handles (draggable)   |
|                                                           |
|  Regions:                                                 |
|  #  | Start    | End      | Duration | Name      |       |
|  1  | 0:00.000 | 0:01.234 | 1.234s   | cut-001   | [▶][✕]|
|  2  | 0:01.500 | 0:02.800 | 1.300s   | cut-002   | [▶][✕]|
|  3  | 0:04.000 | 0:05.100 | 1.100s   | cut-003   | [▶][✕]|
|                                                           |
|  [ + ADD REGION ]   [ SAVE ALL CUTS ]                     |
+-----------------------------------------------------------+
```

**Workflow:**
1. User picks a source WAV from the SD card (`GET /sd/ls` to browse)
2. Device streams the WAV to the browser via `GET /sd?path=<file>` — decoded with Web Audio `decodeAudioData()`
3. Browser draws the waveform on a canvas (peaks downsampled to canvas pixel width)
4. User adds regions by clicking/dragging on the waveform canvas; each region has a start and end handle
5. Each region can be previewed (played in-browser using the decoded AudioBuffer slice)
6. User names the output folder; clicks [SAVE ALL CUTS]
7. Browser slices the AudioBuffer per region, re-encodes each slice as a 16-bit WAV using a small inline WAV writer (no library), and uploads each via `POST /upload?path=<folder>`
8. Device saves each to `/sdcard/<folder>/<name>.wav` — immediately available in the sound browser

**WAV encoding (in-browser, no library):**
```javascript
function sliceToWav(audioBuffer, startSample, endSample, sampleRate) {
    const numFrames = endSample - startSample;
    const numChannels = audioBuffer.numberOfChannels;
    const byteLength = 44 + numFrames * numChannels * 2;
    const buf = new ArrayBuffer(byteLength);
    const view = new DataView(buf);
    // write RIFF WAV header
    writeString(view, 0, 'RIFF');
    view.setUint32(4, byteLength - 8, true);
    writeString(view, 8, 'WAVE');
    writeString(view, 12, 'fmt ');
    view.setUint32(16, 16, true);          // chunk size
    view.setUint16(20, 1, true);           // PCM
    view.setUint16(22, numChannels, true);
    view.setUint32(24, sampleRate, true);
    view.setUint32(28, sampleRate * numChannels * 2, true); // byte rate
    view.setUint16(32, numChannels * 2, true);              // block align
    view.setUint16(34, 16, true);                           // bits per sample
    writeString(view, 36, 'data');
    view.setUint32(40, numFrames * numChannels * 2, true);
    // write interleaved int16 samples
    let offset = 44;
    for (let i = startSample; i < endSample; i++) {
        for (let c = 0; c < numChannels; c++) {
            const s = Math.max(-1, Math.min(1, audioBuffer.getChannelData(c)[i]));
            view.setInt16(offset, s < 0 ? s * 32768 : s * 32767, true);
            offset += 2;
        }
    }
    return buf;
}
```

**New HTTP handler needed:**
- `GET /sd?path=<relative>` — download a file from `/sdcard/<relative>` (stream to browser for decoding). Path jail-checked. Used only for sample cutter source file fetch; not a general file manager.

**New URL additions:**
| URL | What it does |
|-----|-------------|
| `GET /sd?path=<p>` | Download a single file from SD card (sample cutter source fetch) |

**Notes:**
- All slicing and WAV encoding happens in the browser — zero device CPU cost
- The device only serves the source file once and receives the cut files via `POST /upload`
- Large source files (e.g. 50 MB) download fully before the waveform draws; show a progress bar during fetch
- Output sample rate matches source; no resampling

## Open Questions / Decisions Needed

1. **SD slot pin assignment**: confirm ESP32-P4 SDMMC pins don't conflict with MIPI-DSI or GT911
2. **Polyphony limit**: **resolved** — 5 voices per synth lane; not all 16 lanes will run synths simultaneously so worst-case is well under 80 voices total. CPU budget test still useful but no hard ceiling concern.
3. **WAV resampler quality**: kits at 44.1k/22k/48k — linear interpolation is fast but lower quality than sinc; confirm acceptable
4. **Loop quantization**: **resolved** — LIVE mode restarts immediately (flexible, no quantization); SONG mode snaps to the next bar boundary. Toggled by the [LIVE] button; stored as `playback_mode_t` in `song_t`. See section 2.3.
5. **JSON parser**: **resolved** — use **jsmn** (single-header, ~2 KB flash, zero heap, token array on stack). cJSON allocates a linked list per token and requires heap; jsmn tokenizes in-place into a flat `jsmn_token_t[]` on the caller's stack with no malloc. Song/settings JSON is small and read once at load — stack-allocated tokens are fine. See [jsmn](https://github.com/zserge/jsmn).
6. **PSRAM confirmed at 32 MB**: no overcommit concerns; all buffers fit with ~13.5 MB headroom
7. **WiFi AP bandwidth**: **resolved** — only 1 audio client at a time (see item 10); bandwidth concern eliminated. Control WS traffic is negligible (<1 Kbps at 25 Hz playhead + 10 Hz meter). Verify total under load but no concern.
8. **Web Audio latency**: **resolved** — start with 100 ms scheduling buffer; tune down empirically on mobile. Keep WebSocket frame size small (see item 10) to reduce per-frame jitter. Range 50–150 ms acceptable.
9. **IDF version WebSocket support**: **resolved** — `esp_http_server` WebSocket support is available in IDF 5.x which the P4 requires; no extra library needed. The C6 `esp_hosted` SPI transport is transparent to the HTTP/WS stack.
10. **Audio stream format**: **resolved** — raw PCM 16-bit stereo 48 kHz over WebSocket binary frames. Start with PCM; add Opus only if WiFi proves lossy in practice. **Only 1 audio client at a time**: when a new client sends `WS_CMD_AUDIO_STREAM enable=1`, the current audio client's stream is dropped immediately (its ring is freed, its audio flag cleared). The new client takes the slot. This avoids multi-stream bandwidth pressure and simplifies the encode path to a single ring. Frame size: **256 frames = 1024 bytes** (vs 512/2048 previously) — ~5.3 ms per frame, smaller packets reduce per-packet latency jitter on WiFi and fit better in mobile audio scheduling buffers. Bandwidth: 1.5 Mbps (unchanged, single client).
11. **esp_hosted bring-up**: C6 must be flashed with `esp_hosted` slave firmware before P4 WiFi works. SPI pin assignment (MOSI/MISO/CLK/CS + handshake GPIO) must be confirmed against P4 board schematic — no conflict with MIPI-DSI, GT911 I2C, I2S, or SDMMC pins. Add `esp_hosted` to `idf_component.yml` on the P4 side. Verify AP mode + HTTP server + WebSocket all function over the SPI bridge before building Phase 0.4 upload server.
